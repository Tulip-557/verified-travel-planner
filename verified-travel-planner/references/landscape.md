## 二、我们已有的护城河（对标后反而更该守）

读完这些项目，最该记住的是**别人没有的四样东西**：

1. **证据四级 + 四条死线 + 九道闸门** —— 上表**没有一个**有等价机制。
   它们把「票价/营业时间」和「玩法描述」混在一起写，我们划了线且机器可判。
2. **不开 LLM 降级** —— `travel-guidebook` 在高德 API 失败时**自动回退到 LLM 知识库数据**，
   并且写进 FAQ 当卖点。这与本包铁律 1（无地图能力时 POI 与距离一律标 `[D]`，
   不得用模型推断冒充已核实）**直接冲突**。省事，但产出的「已核实」是假的。
   **这是本包最硬的差异化，应当写进对外说明。**
3. **文档自指校验**（`validate_skill.py`）—— 它连自己声明的「19 条规则 / 83 处断言」也一起查。
   对标项目里没有一个对文档与实现的漂移做机器约束。
4. **逐字节回归基线 + 断网自包含** —— 成都示例可整文件 MD5 复现；
   `travel-guidebook` 与 `skills-travel-planner` 都依赖 Google Fonts / Tabler Icons CDN，
   断网即降级。我们的 HTML 0 个外部依赖。

## 三、差距与处置（逐项）

### ✅ 已补（本次落地）

**D1 · 时效只写在规范里，没有机器闸门**
- 缺口实证：`evidence-rules.md` 定义了 6 类阈值（机票 2h / 酒店 12h / 火车票 24h /
  门票当天 / 营业时间 30d / 换乘当日），但**中山事实源全文只有 1 处时戳**
  （`meta.social_intel.checked_at`），分类型时戳根本没落到数据上；
  `feasibility.py` 只查行程层单个 `source_checked_at` 且写死 24h。
  → **判据再漂亮，没有闸门等于没有。**
- 落地：`tools/freshness.py`。中山实测**须重查 3 条（全是门票）**、路线 14 条折叠成一行、
  无时戳 6 条；负向样本（时戳全改到出发日）**0 须重查**，`--strict` 退出码 0/2 正确。
- 对标来源：`china-travel-kit` 的 `last_verified` 字段 + `freshness` 命令证明这条路走得通。

**D2 · 天气能力为零**
- 缺口实证：路书里有「崖口东堤日落」「稻田」这类强天气依赖项，却没有一条命令能查天气。
- 落地：`weather` 命令（复用现有高德 key，零新增依赖）。
  实测 9/28–9/30：**9/30 白天晴、夜间雷阵雨**，自动提示「室外行程建议留一个室内备选」。
- **定位必须说清**：预报窗口只有 4 天，这是**临行前**能力，不是规划期能力。
  所以路书里**不写未来天气**，只写「出发前 3 天再查」。

### 🔴 值得补（按优先级）

**P1 · 从「标注来源」升级到「核验来源」**（借鉴 `citation-check-skill`，249⭐）
- 现状：我们给每条声明标 `[A]/[B]/[C]/[D]`，但**从不验证**标了 `[A]` 的那句话
  是否真的出现在所引来源里。标注是**声明**，核验才是**证据**。
- 借鉴点（该项目的确定性设计值得整套搬）：
  - **Two-Pass**：先抽全部 claim，再逐条核验 —— 保证 same input → same output；
  - **claim 分类树**：统计/比较/归因分类，不同类型不同判据；
  - **精确数字模式**：`96.555% ≠ 97%`，不接受四舍五入后的「差不多」；
  - **Doc-Only 模式**：只允许溯源到给定文档，外部知识一律判为幻觉；
  - **失败即阻断**，不是警告。
- 与本包结合：`social_notes.py --triangulate` 已做「多来源交叉」，那是**来源之间的关系**；
  缺的是**声明与来源之间的一致性**。

**P1 · 测试套件 + CI**（项目自认的 C 级待办，本次调研后应升到 P1）
- 理由：对标项目 `china-travel-kit` 有 `validate` + `unittest discover`；
  `travel-itinerary-planner` 有 6 个测试场景。我们靠**手工跑命令行**验证，
  已经因此漏过几轮（如「改了 itinerary 没回写 slots」）。
- 该被测试锁住的行为：`evaluate` 的 `INFEASIBLE → 退出码 2`、
  JSON 无损往返的行尾嗅探、证据徽章计数、成都逐字节基线、`--compact` 零副作用。
- 加 `gitleaks`（密钥扫描）：本包有凭据文件路径约定，写测试时最容易误提交真实 key。

**P2 · 行程质量评分**（借鉴 `travel-itinerary-planner` 的四维）
- 现状：`evaluate` 只判「排不排得通」（可行性），不判「排得好不好」。
  `score 100` 的意思是「没违规」，不是「方案优秀」——项目文档已反复强调这一点。
- 借鉴：Feasibility 30% / Pacing & Fatigue 20% / Cost Efficiency / Experience Match，
  以及**按同行人构成设活动上限**（solo / family / seniors）与**时差调整**。
- 注意：分数必须**可解释**，否则又是一个「看起来很科学的数字」。
  每项得分要挂到具体活动上，不能只给总分。

**P2 · PDF / 打印版**（借鉴 `travel-guidebook`、`skills-travel-planner`）
- 现状只有 HTML。手机看够用，但「打印成册带上路」是真需求。
- 代价要说清：PDF 需要 Playwright + Chromium（**~300MB 第三方依赖**），
  这会**打破「零第三方依赖」这条护城河**。
- 折中方案：PDF 作为**可选附加产物**，不进核心链路；核心闸门仍零依赖。
  实现上优先用浏览器自带的「打印为 PDF」（用户手动，零依赖），而非内置 Playwright。

**P3 · MCP 化**
- `china-travel-kit` 把同一数据层同时供 CLI / HTTP / MCP 三种接口。
  我们只有 CLI，意味着**别的 agent 无法直接调用**本包的能力。
- 值得注意：本包是 skill（被 agent 读的说明书 + 脚本），MCP 是另一种分发形态。
  对「让别人用上我们」有帮助，对「我们自己产出更好路书」帮助有限 → P3。

**P3 · TSP 地理聚类优化建议**
- 现状：`evaluate` **校验**动线，不**优化**动线。中山 D2 卡到 719 分钟是手工挤出来的。
- 借鉴：`travel-itinerary-planner` 的地理聚类 + TSP 降折返。
- 边界：优化器**只出建议，不自动改事实源**——自动改会让「每个数字有来源」失效。

**P3 · 浏览器插件路线**（借鉴 `xiaohongshu-mcp` 的 x-mcp 版）
- 现状：AUTH 档走 CDP + 独立 profile + 扫码登录，步骤多。
- 借鉴：插件在**用户自己的浏览器里**运行，复用真实登录态与真实 IP，
  **没有服务器 IP 风险**——这恰好命中我们实测到的风控根因（IP 风险）。
- 属外部工具形态，不在本包内实现，但**应写进 `social-login.md` 当作更省事的替代路径**。

### ⛔ 明确不建议做（含理由）

| 候选 | 为什么不 |
|---|---|
| 装 MediaCrawler / 签名对抗类采集 | 非商业学习许可，与本包 MIT 分发冲突；签名对抗路线与「遇风控一次即停手」铁律对冲；换来的仍只是 `[C]` |
| LLM 知识库降级兜底 | 与铁律 1 直接冲突。对标项目这么做是它的选择，我们不能 —— 宁缺勿假 |
| 直连小红书/抖音 | 2026-09-27 实测为**风控**（非登录墙），登录也解不开；已定性 |
| 抓取商业攻略站（携程/点评/马蜂窝）当数据源 | `china-travel-kit` 的数据原则第 4 条同款立场；且版权与许可风险 |
| 用星数当采纳依据 | 上表里 4⭐ 的项目（`travel-itinerary-planner`）提供的思路比 16k⭐ 的更贴我们的问题 |

## 四、一句话结论

**本包的独特价值不在功能数量，而在「不骗人」——证据分级、死线、闸门、自指校验，
这些在对标项目里全是空白。** 因此补功能的顺序应当是：
**先补那些让「不骗人」更可执行的（时效闸门 ✅、来源核验 ✅、测试套件），
再补那些好用的（天气 ✅、质量评分、PDF），最后才是好分发的（MCP）。**

对标里最容易走偏的一条是「高德失败就回退 LLM」——那是把可用性放在可信度之前。
本包的选择相反，且应当一直相反。

## 五、源核验落地后：下一步候选（2026-09-27 22:40 补）

来源核验（`source_audit.py`，第五道闸门）上线并首次跑真实产物后，可信度链条上
还差哪几块、哪些值得做、代价是什么——逐条写清，供排序用。

**P1 · 来源留痕 + 快照比对（源核验的自然下一层）**
- **缺口**：源核验只审「标注纪律」（标得配不配），**不审「内容真实」**（标了 `[A]`
  的那句话是否真出现在所引来源里）。后者做不了，是因为事实源**只存结论、不存原始返回**。
- **做法**：生成阶段把原始证据落盘——高德 POI/路线返回体、网页正文摘录，存
  `证据快照/<目的地>/<日期>/`，与声明一一对应；再加一条闸门做「声明 ↔ 快照」比对
  （数字、名称、时戳是否在快照里找得到）。
- **收益**：这是**唯一**能机械验证「内容真实」的路径；也让「三个月后重开旧路书」有据可查。
- **代价**：事实源结构变复杂（事实源的每个动态数字要挂快照键）；快照有体积与隐私问题
  （含个人查询记录，须 `.gitignore`）。
- **不做的风险**：`[A]` 永远只是个方括号——纪律再好，也拦不住「写了 `[A]` 但来源里没有」。

**P1 · 测试套件 + CI（工程保障，对标后从 P3 升 P1）**
- **弹药已备**：本次源核验的负向样本（坏事实源，6 类违规）就是第一批测试用例；
  五个工具各自都跑过正负向实测，缺的只是「把它们固化成断言，每次改动自动跑」。
- **做法**：`tests/` 目录 + 标准库 `unittest`（**不引入 pytest**，保住零第三方依赖），
  覆盖：徽章解析 / 死线归属 / 语境收窄（防误报回归）/ 时效阈值 / 闸门退出码三态。
  CI 用 GitHub Actions，加 `gitleaks` 防密钥误推（高德 key 已 gitignore，但规则须机器守）。
- **代价**：无——零依赖测试套件与现有理念完全一致。

**P2 · 证据健康度一页纸（`source_audit --json` 已有数据源）**
- 现在 A/B/C/D 分布、死线违规、须重查项分散在三个工具的输出里。
- 做法：合并成交付附页「本次路书可信度概览」——几枚 `[A]`、几项 `[D]` 及出路、
  几条须出发前重查。**让用户一眼看到「这份路书哪里最硬、哪里最虚」**。
- 代价：低（纯汇总）。风险：别做成「分数」——分数会诱发刷分，清单不会。

**P2 · 改版审计（事实源 diff）**
- 路书改版（v1→v2）时，机器列出「哪些声明变了、等级变了」：`[A]`→`[C]` 的降级
  必须显式出现，不能悄悄发生。中山 v1→v2 是人工比对的，可机械化。
- 代价：中（需定义「可比对的声明单元」）。

**P2 · 一键交活脚本**
- 九道闸门 + 时效 = 11 条命令要记。做法：`tools/ship.py` 顺序跑完、
  汇总成一张交付清单（哪几道绿、哪几条须人工）。**不合并工具，只编排**——
  每个闸门仍独立可跑、独立退出码。

**P3 · 目的地包（把「中山」变成可复用资产）**
- 现状每个目的地从零做。做法：把「事实源 + 社媒线索 + 自检结果」打包成目的地模板，
  新目的地复制起手，历史核对结论可复用（**但必须带时戳过期机制**，否则复用会变成
  「用过期的数当新数」——那正是本包最不能接受的）。

### 方向选择：三条路，本包该走哪条

| 方向 | 内容 | 判断 |
|---|---|---|
| **① 更可信**（纵深） | 留痕 + 快照比对 + 测试套件 + 改版审计 | ✅ **主方向**。与护城河同向，别人不做的我们做深 |
| ② 更好用（横向） | 质量评分 / PDF / 交互地图 / 多目的地 | ⚠️ 选择性做。**PDF 会打破零依赖**，只做可选附加；评分要挂到活动不能只给总分 |
| ③ 更好分发（形态） | MCP / 插件 / 网页版 | ⚠️ 排最后。分发不改善路书质量；MCP 化对「让别人用上」有用，对「我们做得更好」帮助有限 |

**一句话**：本包的天花板不在功能表长度，而在**「能不能把「不骗人」做成机器可验的闭环」**。
来源留痕是这条路上最硬的一块——它做完，「标注」才真正变成「证据」。
