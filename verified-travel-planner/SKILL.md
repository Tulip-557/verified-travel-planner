# 可核验旅行规划器 · verified-travel-planner

## 这套 skill 为什么存在

看过的旅行规划 skill 大多栽在同一个地方：**AI 编数字**。车程是估的、票价是旧的、营业时间是记的——看着像那么回事，落地时每一条都得自己重查。

本 skill 从两个开源标杆各取所长：

| 来源 | 取了什么 | 一句话 |
|---|---|---|
| **tanweiping1012/travel-planner**（实证派） | 数据可信度机制 | **模型不生成任何数字**——所有数字来自工具调用，带来源和时间戳 |
| **awangwang123/jianhao-travel-planner**（校验派） | 交付质量机制 | **错了必有钩子拦**——不靠提示词祈求，用脚本在交付前硬校验 |

合起来就是一句话：**数字不骗人，错误拦得住。**

---

## 铁律（任何阶段不可违反）

1. **数字必溯源**：距离/时长/票价/余票/营业时间/门票价，**必须来自工具调用或联网实查**，禁止模型凭印象生成。每条带来源 + 查询时戳，格式 `¥350（2026-09-27 13:00 查·长隆官方公众号）`
2. **未核实必标注**：查不到就写「未核实·请自行确认」，禁止含糊带过、禁止编造、禁止用"大约""通常"模糊掉
3. **单一事实源**：**事实源 JSON 是唯一事实源**，md 与 HTML 都是派生/渲染产物。改任何决策点必须**当批回写 JSON**，只改 HTML = 欠账。禁止平行维护两份内容文件
4. **动线不绕路**：按地理位置组织每日行程，跨区必说明理由；每对相邻地点必须有真实路线，禁止估算
5. **天气定节奏**：避暑模式（早出+午休+晚出）/ 防雨模式（上午户外+午后室内），按实查天气切换
6. **安全游玩第一位**：台风/暴雨/雷暴/沙尘预警下，户外项目果断砍或改期。宁可留遗憾，不冒险
7. **预算诚实**：隐藏成本单列不漏——过路费/停车费/观光车/行李托运/服务费/讲解费。多档票价（单票/联票/含车票）先拆清结构再算账，防重复计价
8. **只读边界**：不购买、不预订、不支付、不候补、不改签。不输入密码/验证码/身份证/支付信息。不导出 Cookie/Token。不点攒收藏关注评论发布。不绕验证码/登录墙/风控
9. **能力先测后报**：不许凭"文档说"或"看起来像"就断定某数据源不可用。**试一次，再报结果**。没试就说"没试过"，不说"不行"

## 证据分级（本 skill 的核心机制）

每条信息必须归入**唯一**一个证据等级，等级决定它能走多远：

| 等级 | 标记 | 来源 | 能做什么 |
|---|---|---|---|
| **A·工具实证** | `[A]` | 地图 API 返回的 POI/坐标/路线、12306 车次余票、官方渠道门票价 | 可直接写入路书，作为硬事实 |
| **B·多源交叉** | `[B]` | ≥2 个公开平台信息一致（点评高分 + 地图在营 + 攻略多帖提及） | 可进正文推荐，标注来源与核实日期 |
| **C·单源线索** | `[C]` | 只有 1 个来源，或来自 UGC 笔记/搜索摘要 | 只能进备选池，必须标注「单源·待核」 |
| **D·未核实** | `[D]` | 查不到 / 来源失效 / 相互矛盾 | 如实写「未核实」，给用户人工确认方式 |

**分级使用规则**：

- **票价、车次、余票、营业时间、开放状态** 只能取 `[A]`。任何 UGC 内容（小红书/抖音/B站）**不论说什么**，都不能作为这几类的来源——那些必须来自官方渠道、地图 POI 或 12306
- **UGC 内容只能用于**：路线顺序建议、人流/排队体感、季节时机、体验描述——且必须归为 `[C]` 或配合其他源升为 `[B]`
- **A 级信息有时效**：票价/余票/航班在交付前**必须重查一次**（默认阈值：火车票 24 小时内有效，机票 2 小时，门票当天）；重查失败就标「参考价·需现场确认」
- **矛盾不裁决**：两个源给不同答案时**并列写出**，说明各自来源，不擅自选一个

## 工作流

```text
阶段 0  需求采集（逐项问清，缺失用默认值并声明）
  ↓
阶段 1  能力自检（测数据源可用性，记录降级项）
  ↓
阶段 2  目的地筛选（给方向，拍板后再做详细方案）
  ↓
阶段 3  实查复核（硬数字 · A 级信息采集，逐条带时戳）
  ↓
阶段 3.5 社会情报采集（玩法与体验 · B/C 级；**默认执行**，跳过须声明）
  ↓
阶段 4  路书产出（六维度 + 双写同步 + 情报来源声明）
  ↓
阶段 5  交付自查（30 项机械核对，机械可查部分全绿才可交付）
  ↓
阶段 5.5 交付分发（微信传文件为首选，附未核实项清单与覆盖声明）
  ↓
阶段 6  行程中陪伴 / 复盘回流（情报回流进库，供下次复用）
```

> **阶段 3 与 3.5 是一根扁担的两头**：3 采「硬数字」（车程/票价/营业时间/余票），
> 3.5 采「玩法与体验」（怎么玩、什么时候去、值不值得多待）。**两者信息不重叠、
> 证据不互相顶替、死线不互相越界**——3.5 永远不产出数字，3 也永远不告诉你哪里好玩。

### 阶段 0 · 需求采集

逐项问清，**已知的跳过，缺失的用默认值并明确声明**（默认值被静默应用 = 用户分不清是他说过的还是你替他定的）。

- **时间窗**：哪天走哪天回？能否请假？
- **当前状态**（决定工作模式）：计划中（规划模式）/ 已出发在路上（陪伴模式）/ 已到目的地（执行模式）
- **人数结构判定两问**：①几个人什么关系（兄弟/闺蜜/情侣/家庭带娃/家庭带长辈/混合/一人行）②有无体力特殊成员
- **同行者档案**（非一人行必采）：口味下限 / 体力作息 / 兴趣类型（自然/人文/美食/拍照）/ 自驾几人能开 / AA 规则
- **交通方式**：自驾 / 高铁 / 飞机 / 卧铺（可组合）
- **预算档位**
- **硬约束**：排除地区、去过的、忌口、体力上限
- **已计划前往**（`planned_places`）：有没有已经定好要去的点？订票/预约了没有？
  与「硬约束」不同——它采的是**用户心里已经有的行程锚点**，路书要优先串进去；
  其中订了票的（`BOOKED`）时间窗固定，排程必须让路
- **玩法取向**（必问，无安全默认值）：深度体验 ↔ 特种兵暴走
- **内容目的**：纯玩 or 要出内容（默认要出）
- **偏好锚点**：出片 / 美食 / 避暑 / 人少 / 文化（排序）
- **作息**（必采，只问事实不定型）：全队一般几点起？有人能起早吗？有人晚上精神吗？有没有一定要在特定时段做的事（夜爬/拍星空/看日出/夜景亮灯/逛早市/赶海）？**没答默认睡到自然醒**

**一人行专属**：是否首次独行 / 夜归安全底线 / 报平安对象与频率
**省力慢游专属**（有长辈/腿脚不便/带娃时）：连续步行上限 / 台阶承受度 / 午休是否刚需 / 慢病用药 / 行动辅助

> 称呼同行者用自然口语词：长辈/老人/爸妈/孩子。不用「祖辈」「老人家」这类生硬 AI 腔。
> 统称「省力慢游」而非"年老体弱"——说的是方案属性，不是人的属性。

**采集完跑一道机械校验**——有些字段**没有安全默认值**，缺了就不该开工：
人均 2000 和全队 2000 差一倍；体力等级决定哪些行程根本排不通；玩法取向决定每天排几个槽；
能不能用浏览器是别人不能代答的授权。

```bash
python "<SKILL_ROOT>/tools/travel_planner.py" validate-request --input 需求.json
```

`status` 有三个值：`READY`（可开工，**不要再问任何问题**）／`NEEDS_CLARIFICATION`
（有缺项或冲突，**一次问完**，别挤牙膏）／`INVALID`（有错值，先让用户改再调研）。
脚本同时会列出**哪些项是按唯一合理读法假设的**——那些必须如实写进路书，
不许当成用户说过的话。

### 阶段 1 · 能力自检

**在开始规划前，先测一遍数据源，别等用到才发现不可用。**

先跑体检脚本拿基线（默认只读探测，不联网）：

```bash
python "<SKILL_ROOT>/tools/doctor.py"          # 解释器 / 时区库 / 引擎 / key / 资产
python "<SKILL_ROOT>/tools/doctor.py" --live   # 顺带实测高德连通性
python "<SKILL_ROOT>/tools/social_source.py" --doctor   # 社媒采集渠道：哪几条路走得通、天花板多高
python "<SKILL_ROOT>/tools/social_login.py" --check     # AUTH 档：登录态通路是否就绪（浏览器 / CDP / profile）
```

它会把每个能力标成 `READY` / `DEGRADED` / `MISSING`，并直接给出降级口径。然后逐项实测并记录状态：

| 数据源 | 测什么 | 状态标记 |
|---|---|---|
| 地图服务 | 取一个真实 POI，确认返回坐标 | `READY` / `NO_KEY` / `BLOCKED` |
| 铁路查询 | 查一对真实车站的当日车次 | `READY` / `UNAVAILABLE` |
| 网页实查 | 打开一个 OTA 或官方页面 | `READY` / `LOGIN_REQUIRED` / `BLOCKED` |
| 浏览器 | 确认当前环境有无交互式浏览器 | `available` / `unavailable` / `unknown` |
| 社媒采集 | 跑渠道能力矩阵，看有几条 `READY`、证据天花板多高 | `READY` / `UNCONFIGURED` / `BLOCKED` |
| 登录态采集 | 跑 AUTH 档自检：浏览器 / CDP 通路 / 登录态 profile | `READY` / `UNCONFIGURED` |

**降级规则**（缺什么就明确少给什么，不许装作完整）：

- 无地图 → **不得声称验证过 POI 或地面路线**，距离时长一律标 `[D]`
- 无铁路查询 → 不得给实时余票，改用只读网页查或标 `[D]`
- 无浏览器 → 请用户提供已知信息，或声明该渠道不可用
- **境外目的地**：多数国内地图服务对境外查询**不返回空，而是返回同名国内地点**（查「东京」得广西一个叫东京的村庄，坐标格式完全正常）。必须识别并**拒绝**这类结果。境外模式下车次/地面路线无 `[A]` 级来源，路书要写明哪些检查没做

> 🔴 **不许把"文档说"当结论**。曾经犯过的错：还没匿名试过就断定小红书必须登录（确实是，但是猜中的）；还没截图就读不到图片（实际完全可读，且图片里才有明细账单）。**每个"不行"的结论，都要有一次真试过的记录。**

### 阶段 2 · 目的地筛选

列 3-5 个候选，每个查：①极端天气预警 ②季节适配 ③交通耗时 ④出片度 ⑤特色度 ⑥**当季限定**（联网实查"当季有什么"，不内置静态表——会过期）

输出：**1 首选 + 1-2 备胎 + 明确劝退项**（附一句话理由）。用户拍板前不做详细路书。

### 阶段 3 · 实查复核

**这是 A 级信息的采集阶段，每条都要带来源和时戳。**

**天气**：行程期间逐日预报 + 关键日逐时段预报（午后雷阵雨窗口 / 日落前后 / 夜间）。午后雷阵雨 ≠ 全天不能玩，按逐时段决策。另查极端天气历史。

**门票 / 预约**：
- **检索时点 = 当下**——出票务信息那一刻联网查，**不许沿用本次会话早前结果，更不许沿用记忆里的价格**
- **官方源优先序**：景区官网/官方公众号 > 官方 App > OTA 在售页 > 游客攻略（攻略只能当线索）
- 每条价格写死时戳：`¥350（2026-09-27 13:00 查·长隆官方公众号）`
- 查不到官方源 → 如实写「官方渠道未查到，请自行比价」+ 给比价指引（官方公众号/小程序/点评/地图/直播间看哪个优惠多），**并提醒比对好日期**（不同渠道挂的可能是不同日期档票价）
- 网页价与官方价不一致 → **并列写出**，不擅自取其一
- 高热度需预约景点按「提前 5 天」倒排预约节点，放票日即设提醒
- **多档价格先拆结构**：单票/联票/含车票并列时逐档核对官方在售商品名（联票含不含景交/观光车），防重复计价

**交通**：车次/航班时刻、末班车衔接、**换乘留 ≥1 小时**。余票必须来自实时查询，禁止用攻略里的旧数据。

**店铺**：营业状态、人均、招牌菜、排队情况。

**实查纪律（四条）**：
1. **止损点**：同一信息最多搜 **2 轮**（含换源换路径），仍无结果 → 标「未查到」+ 给用户人工选项，**禁止循环重试死磕**。遇验证码/风控**一次即停手换路径**
2. **时效标注**：每条关键信息标"哪年的"。营业类信息超 1 年必须补查现状
3. **用户线索双向校验**：用户给的线索可能记错——核实结果与其记忆不符时如实回告，**不硬凑用户期待**
4. **AI 摘要不可作证据**：搜索引擎返回的 AI 生成摘要只当线索，写结论前必须落到具体页面的实锤

**并行纪律（阶段 3 的主要提速点）**：

慢的不是「查得细」，是**把互相不依赖的查询排成一队**。一条一条发，每条都要等上一
条回来才开工，墙钟时间 = 各条之和；能并行的合成一批，墙钟时间 = 最慢那一条。

判据只有一条：**换实体 / 换主题的查询互相独立，同一消息内一次发完；
后一条要用前一条的结果（先定景点 → 再查该景点营业时间），才串行。**

| 典型分组 | 组内的查询互相独立吗 | 动作 |
|---|---|---|
| 天气（逐日预报 / 极端天气历史） | 是 | 一组一并发出 |
| 门票预约（各景区各自的价格 / 预约规则） | 是 | 一组一并发出 |
| 交通（车次 / 航班 / 末班衔接） | 是 | 一组一并发出 |
| 店铺（营业状态 / 人均 / 招牌菜） | 是 | 一组一并发出 |
| 「先定去哪个景区」→「再查它的闭馆日」 | **否** | 必须串行 |

**并行的边界（别把提速做成挨封）**：
- 并行指**多个不同来源同时开工**，不是**同一站点同一秒并发猛刷**。同一域名一批
  控制在个位数，超了就是自己制造 `10021`
- 引擎侧高德调用已自带退避重试，**不要再手搓 sleep**（`AmapClient._get`，
  见 `references/experience.md` 第 4 条）——空闲时它不减速，被限流才退避
- 并行的**轮次**仍受止损点约束：每条信息最多 2 轮。并行不给你多试几次的额度
- 触发风控/验证码：一次即停手换路径，不重试、不加并发

### 阶段 3.5 · 社会情报采集（默认执行 · 补玩法与体验，不补数字）

**这不是可选项，是每次生成攻略的默认动作。** 一个目的地只有「在哪、多远、几分开」
是撑不起一份好路书的——「去了该干嘛、什么时候去、人多不多、值不值得多待」正好是
社媒的主场，而这几类信息地图 API 一条都给不了。

**它为什么敢默认化**：三条死线（票价 / 营业时间 / 车次余票 / 距离车程）把它和 A 级数据
彻底隔开——社区知识只能塑造路线，永不作事实呈现。**越界风险是被机器拦住的，
所以它可以放心地每次都跑**；判据在 `tools/social_notes.py`，不在自觉。

#### 触发规则：默认跑，跳过要留痕

| 情形 | 动作 |
|---|---|
| 默认 | **跑**。产出线索卡 → 追加情报库 → 把声明写进 `meta.social_intel` |
| 纯过境（目的地停留 < 半天） | 可跳过，**须写明理由** |
| 用户明说不要社媒内容 | 可跳过，**须写明理由** |
| 目的地无公开内容（无人区 / 私人领地） | 可跳过，**须写明理由** |

> 跳过允许，**静默跳过不允许**。声明落在 `meta.social_intel`，渲染器会把它变成
> `#overview` 顶部的「情报来源」条，交付自查第 **㉗** 项就查它。
> 判据是**留痕**而不是**必须采到**——「报『没有』比报假的『有』值钱」。

#### 先说实测结论（2026-09-27 本机，无头 Edge 匿名）

| 目标 | 结果 |
|---|---|
| 小红书（首页 / 搜索页 / 笔记页） | `安全限制 · IP存在风险 · 300012` |
| 抖音（搜索页） | `验证码中间页` |

两者都是**风控拦截而非登录墙**——所以「登录一下就能读」是错判。按铁律 8，
遇风控**一次即停手换路径**，不重试、不换 UA、不绕。

#### 三条路径 = 可复用来源清单（可靠性降序）

① **官方文旅发布**（首选，可到 `[B]`）——政府/协会/媒体的榜单与精品线路。
  搜「<目的地> 文旅 精品线路 / 十大景区 / 官方推荐」。**它给的是「线路组合 + 玩法定性」，
  恰好完全不碰死线**，是性价比最高的一档。
② **搜索引擎索引**（`[C·单源]`，`connector_type = web_search_fallback`）——能拿到攻略站
  完整正文，**但索引摘要不是第二来源**（同源转载，不能互证）。
③ **用户投喂**（`[C·单源]`，`connector_type = user_provided`）——真实用户在真实网络下
  能打开你打不开的页面；仍须记平台与账号 ID。

三条路径的**完整打法、能力矩阵与判据边界**见 `references/social-intake.md`。

#### 渠道层：21 条渠道、五档状态（`references/social-sources.md`）

三条路径只是「怎么走」，还得知道「这台机器上哪几条走得通」。机器可查：

```bash
python "<SKILL_ROOT>/tools/social_source.py" --doctor              # 能力矩阵（本机实测状态）
python "<SKILL_ROOT>/tools/social_source.py" --plan 中山 --days 3 --month 9月   # 生成关键词组
```

渠道分五档：`OPEN` 零配置可用 ｜ `OPTIONAL` 需一次配置 ｜
`AUTH` 需用户授权登录（**风险落在用户账号上**）｜ `GATED` 需资质或付费 ｜
`BLOCKED` 实测风控不可达（**登记在这儿就是为了防止反复重试**）。
**证据等级天花板写在渠道上，不写在内容上**——代理抓取换的是出口 IP，不是可信度，
所以抓取类渠道一律封顶 `[C]`；**唯一能到 `[A]` 的是平台官方开放平台接口**，
而国内内容平台的这类接口多面向企业/广告/电商场景，个人行程里通常用不上。

**实测后修正过的三条判断**（原以为 → 实际）：

| 原以为 | 实测 |
|---|---|
| 小红书/抖音读不到 | 成立，且**知乎 / 马蜂窝也不可读**——是**国内 UGC 平台的整体姿态**，不是个别站点 |
| 官方发布只能看搜索引擎转述 | **错**：微信公众号原文**可整篇读**（4.7 MB DOM），官方渠道的信息量被低估了 |
| 国内社媒没有可读的 | **错**：**微博**与**B站**搜索页零配置可读——补上了「实时热点」与「话题发现」两块空白 |

**五条扩展路径**（按性价比降序）：
① **把官方渠道吃干榨尽**——多级官方源（市文旅局→省文旅厅→政府新闻发布厅→地方党媒）
+ 多类发布物（精品线路 / 节庆档期 / 消费券 / 新开放景区 / **名录类**：A 级景区名录、
**诚信店名单**——**唯一有官方背书的「店单」来源**，对吃/店选择的价值高于任何 UGC）
+ 「目的地 + 月份」的档期问法。**零成本，优先做这个**；
中山就是靠它拿到全场价值最高的一条线索。
② **加配抓取代理**（连接器 / 云采集 SaaS）——解决「抓得到」，不解决「更可信」。
③ **用你自己的登录态（AUTH 档，要用户拍板）**——三种强度递增：
`logged_in_cdp`（独立 profile 扫码一次 → 之后**只读单页**，`tools/social_login.py`）｜
`local_crawler`（MediaCrawler 类，能拿几百条，但**非商业许可 + 账号风险，默认不启用**）｜
`third_party_api`（TikHub 类，按次付费，仍是第三方聚合 `[C]`）。
**记住总纲：登录只提升覆盖度，不提升证据等级**——UGC 天花板照旧 `[C·单源]`，
而账号风险由用户承担。**用账号风险去换 `[C]` 级线索，多半不划算。**
完整权衡与操作步骤见 `references/social-login.md`。
④ **用户投喂常态化**——阶段 0 就顺带问一句「有没有刷到过相关笔记/视频？」；
截图转录须标 `manual_transcript`。**这是「用户授权」最轻的一档，零风险。**
⑤ **开放平台接口**——有资质才做；**别为了等级好看去申请一个用不上的应用**。

**合规三条铁律**：只读公开内容（默认不登录；AUTH 档登录后也只读、不互动、不批量）｜
不绕风控（一次即停手）｜
不采个人信息（昵称与公开账号 ID 可记，联系方式与行程轨迹不可）。
`crawler_saas` / `local_crawler` / `third_party_api` 三条路的**合规责任在使用者**——
尤其批量采集，最大风险不是抓不到，**是用户自己的账号被限**。

> ⚠️ **判风控要看返回体，不要 grep 关键词**。实测踩到过：B站搜索页里有「登录」按钮文案，
> 被第一轮探针误判成登录墙；实际页面取了 1.1 MB、1345 个视频卡片，完全可读。
> 正确判据是**返回体特征**——状态页标题、错误 JSON、WAF 脚本——而不是页面里出现了什么词。
>
> ⚠️ **「有 cookie」≠「已登录」**。匿名访问同样会下发设备/风控 cookie，
> 于是那些域就出现在 profile 里了。判登录态看**标志性 cookie 名**
> （`web_session` / `SESSDATA` / `sessionid` / `SUB` / `z_c0`），不看「有没有 cookie」。
> **判据要落在「是不是」，不是「有没有」。**

#### 三份可复用资产（每趟都要回流）

情报不是用完即弃的检索结果，是**跨行程滚雪球的数据资产**：

| 资产 | 位置 | 谁写 | 下次怎么用 |
|---|---|---|---|
| **线索卡** | `社媒线索_<目的地>.json` | `social_notes.py -o` | 先读旧卡看还差什么、只补新增；`--merge` 增量并入 |
| **玩法情报库** | `情报库/玩法情报_<城市>.md` | 阶段 6 复盘时追加 | 下次去同城 / 邻近城市**先读它**，不重搜已知结论 |
| **信源名单** | `references/sources.md` | 途中刷到靠谱内容就补 | 直接成为下一趟的采集起点 |

`--merge` 是「复用」的机器实现：按 `url` 去重（本次重采到的用新的），旧条目**保留**
并标 `carried_over`，超期再加 `stale` 等下次重核。**旧条目不会因为「这次没搜到」就消失，
也绝不会冒充新鲜情报。**

### 阶段 4 · 路书产出（六维度）

**产出管线——数据与模板分离**：

```
路书_<目的地>.json   ← 唯一事实源（字段见 references/ludbook-schema.md）
        │  tools/render_html.py
        ▼
路书_<目的地>.html   ← 派生物，禁止手改（改了下次重渲染就丢）
```

上游见好把 HTML 骨架固化了，但落地是「复制骨架 → 手改常量 → 手填区块」，它自己
在 SKILL.md 里把「数据与模板分离」标为理想态。本 skill 把这一步补上：

- 骨架的 `<style>` / 三个 `<script>` / IA / 导航全部由 `assets/路书_基准骨架.html`
  原样带入，所以**「CSS 指纹一致」是结构上不可能出错，而不是靠提示词祈求**
- 缺值、区块空、残留占位符，渲染器**直接拒绝产出**——不生成半成品
- 渲染后接 `--verify` 跑版式一致性校验。**不绿就是没做完**
- 改内容一律改 JSON 重渲染。**从 `assets/路书事实源模板.json` 复制开始**

**为什么值得这么改**：老做法要人工同步「md 事实源」与「HTML 成稿」，上游为此吃过
「改了 HTML 没改底稿、重建时 15 项修正全丢」的亏。现在 HTML 是纯派生物，不存在两
份内容文件，那条错误路径直接消失。

文件命名：`路书_<目的地>.json` → `路书_<目的地>.html`（草稿加 `_v1` 后缀）。

**双版本：同一事实源，出两份路书**

```
路书_XX.json ─┬─ render_html.py              → 路书_XX.html          （完整版 · 策划件）
              └─ render_html.py --compact    → 路书_XX_精简版.html    （精简版 · 执行件）
```

**为什么要有精简版**：反馈很一致——完整版内容太多，路上没耐心翻。
但**删信息不是解法**，「收进 `<details>`」也不是：后者只是把内容移出首屏，
**字数与 DOM 长度一分未减**（中山实测：全篇只省 15%）。

**真正的解法是把精简版定位成「执行件」**——路上照着走的那一份。
判据因此不是「怎么变短」，而是「**这件事是边走边看，还是出发前翻一次**」。

| 做法 | 解决什么 |
|---|---|
| `sections` 与 `days[].slots[].body` **都支持 compact 双档**（同一套机制、同一个取档函数） | `days` 占全篇约 65%——只压 `sections` 等于没压（实测只省 15%） |
| 首屏注入 **「一眼看全 N 天」速览表**，每行可点跳当天 | 「不知道从哪看起」+「看到一半忘了前文」 |
| 资料区（住宿 / 预算 / 美食全表 / 特产 / 备选）**不渲染正文**，只留一行「本版不展开」指引 | 与速览表对读者的承诺一致：本页没有的，就是真的没有 |
| 逐日注释：`food` / `stay` / `warn` 展开，`metro`（今日交通汇总）收进 `<details>` | 当天随时要用的展开，出发前对一遍的收起 |
| 每天配图**收敛为 1 张**（原按天配多张时） | 手机滚动负担 |

实测（中山，3 天）：完整版 14072 字 → 精简版 **7837 字（55.7%）**。
口径 = `compact_check` C5（全文去标签去空白）；按「只数各 section 正文」的探针口径则是
7782 字（55.3%）——**两个口径都可复现，别混用**（差别是首屏速览表那几十字）。

**几条硬约束**（别绕）：

- **精简版与完整版共用同一骨架**，所以 CSS 指纹、IA、导航、30 项自查口径**完全一致**——
  精简版**不是另一套模板**，`consistency.py` 与 `ludbook_check.py` 照跑，全绿才算交付；
- **两版都要过闸门**。精简版若为了「短」而丢了 `[A]`/`[B]` 徽章、`[D]` 清单、
  未核实出口、餐行，照样红灯——**短不能成为降标准的理由**；
- **`compact` 档必须自己带来源与查询时戳**，不能只靠段内继承——
  中山实测：删掉 `tips` 段里唯一那句「查询于 2026-09-27」，段内两条 `[A]` 立刻从 WARN 变 **FAIL**；
- **压缩不能丢掉强制约束里的数字**（末班 / 停止入场 / 寄放 / 留足余量 / 行程时长）。
  这是 `tools/compact_check.py` 的 C3，已用负向样本验证能拦；
- **闸门 `tools/compact_check.py`**（5 条规则 C1–C5，有 FAIL 退出码 2）。
  写法规则、四轮削减实测、三个坑见 `references/dual-version.md`。

**结构**：

1. **头部**：人员/时间/天气实况/核心节奏 + **地理归属一句话**（不假设用户知道目的地行政区划关系）
   + **情报来源声明**（阶段 3.5 的交代，由 `meta.social_intel` 自动注入 `#overview` 顶部）
2. **倒计时行动清单**：时间敏感动作按 T-N 天倒排——T-5 高热度预约（放票日设提醒）/ T-3 普通预约+抢票 / T-1 天气终判 / 退改截止提醒（火车票 24-48h 内扣 10%）。**重点项加粗+警醒标志**
3. **预约状态表**：什么要约、什么不用约、放票时间、**预约截止日**、取消规则、约满兜底
4. **逐日行程**（每天吃/玩/住/行/拍五块）：
   - **吃**：**美食选择池**两层——定档（正文）+ 备选池（附录）。每家给地址+招牌+人均+排队提示。
     - **正餐线 = 三路交叉**：点评榜单/店铺页 + 地图 POI（评分/营业时间/门牌）+ UGC 攻略。**每个信源单独搜一次，禁止多源合并关键词搜**（互相稀释会漏结果）
     - **早/宵/下午茶线**：地图/点评搜「目的地+早餐/宵夜/下午茶」，给具体店+**营业时间**（每天 2 家左右，"随意"设定）
     - **收录门槛三级**：**R1** 店名+门牌已核 → 收录 ✅；**R2** 无店名但有确切位置引导（"凌晨 4:30 开在菜场旁"）→ 收录 📌+给认店口诀，**仅限信源穷尽后启用**；**R3** 既无店名又无位置、或有负面评价 → 不收录
     - **呈现两层**：日程卡每餐精简内嵌（午/晚只推 1 家，行尾加「更多选择在美食清单」）+ 独立「美食清单」板块（板块名固定，grep「吃饭清单」必须为 0）
     - **餐行机械钩**：每日必须有早/午/晚三行，「园内/高铁上解决」也要有行
     - **三池归属**：使用者点名店只在「博主推荐」彩蛋板块（行程与清单正文全清）；场地型店可留动线但删推荐措辞；主表 = 动线锚点店 + 自找店
   - **玩**：动线/重点/时长/讲解建议。**热度配比 6:3:1**——6 成热门保底 + 3 成冷门惊喜 + 1 成弹性。禁止全热门（中规中矩）或全冷门（拿行程冒险）。特种兵模式改为最大化不同景点数量，每点 20-40 分钟
   - **住**：先选**住宿形态**再选区域。形态按人群：兄弟局=电竞房/民宿套间；一人行=性价比连锁/青旅；家庭=套房/民宿；内容向=特色民宿。再定区域+理由（近动线/近美食）+价位。**信源=三平台同店比价**（同店价差常见一成以上，以可免费取消的低价为锚）
   - **行**：大交通精确时刻 + 市内交通（**哪天开车哪天地铁**）。**自驾/多点位必须出「全程路程时间总表」**（每段里程+正常耗时+节假日预留，估算段标【估算】）。**非自驾必须给公共交通方案**（站/机场→景区班车、景区间衔接、**末班时间**、散场打车难度）
   - **拍**：机位清单 + 最佳时间 + **光线逻辑**（建筑朝向决定顺逆光）+ **特殊场景参数手册**（夜景/雨景/日出夕阳/星空/博物馆/美食，分 iPhone 和安卓）。
     - 🔴 **游玩体验为主体、机位是顺路提示**——禁止把机位串成独立时间块占用行程主体。自检法：读一遍问「这是游客的一天，还是摄影师的一天？」
     - 🔴 **配图挑图先建概念**——先写下地标真实外观特征（重建年份/形制/颜色/标志物），到图库核对拍摄对象+年份再下。**古画/在建照/重滤镜无标志物三类直接跳过**
5. **避雷表**：必须"真实场景+应对"式（❌"注意防晒" ✅"遗址区无遮挡，观光车必坐否则热死"）。面向长辈/官方群体称「温馨提示」
6. **预算表**：逐项+人均。隐藏成本单列
7. **应急表**：每个关键环节给 Plan B（错过车/暴雨/约满/肠胃）
8. **景区示意图**（分散型多景点必出）：手绘 SVG，六要素齐备（指北针/地标插画/文字禁压线入水/动线禁穿水系/支流方向对照真实地图），标注「示意非等比」+数据来源日期
9. **装备清单**：**必须与本趟实时匹配**，禁止通用模板套用。按目的地×季节×天气×温度×环境五要素定制

**作息排程**：
- **家庭游/自由行**：出发日「10 点前后」——**软目标不是闸门**，9 点多出发、10 点半开玩都算达标。真正要拦的是「6-8 点档起床赶路」
- **特种兵**：可提前、可夜排、可连续暴走，按玩法需要排满。三条底线不破：恶劣天气铁律、安全底线、实查纪律
- **早起包/夜游包**：作息敏感型项目一律不进主线，但必须落成两个包——「🌅 早起的人（自愿）」+「🌙 夜游包（自愿）」，写清几点出几点回谁去，标注作息代价
- 🔴 **特殊时段玩法必须主动提出**：凡「有最佳时段、错过就废」的玩法（夜爬/拍星空/日出日落/晨雾/云海/夜景亮灯/灯光秀/早市/赶海/观鸟/夜市），不许因默认晚起就静默砍掉——必须显式交代「项目+为什么非得那个点+作息代价+归入哪个包+不去拿什么补」

**人数结构 × 玩法 × 体力三轴正交**，可任意叠加：

| 模式 | 核心 | 住 | 吃 | 拍 | 节奏 |
|---|---|---|---|---|---|
| 兄弟局 | 玩得爽+性价比 | 电竞房/拼房 | 大排档/烧烤，酒水放开 | 随手拍 | 可叠加特种兵 |
| 闺蜜局 | 出片+氛围 | 双床房/美学房 | 下午茶权重高；**拍照好看的店 ≥ 好吃的店** | **互拍是核心**，机位密度加倍 | 慢，留购物时间 |
| 情侣 | 两人时光 | 大床/景观房加分 | 氛围餐厅 | 互拍+合照，蓝调时段优先 | **浪漫时段 > 打卡数量** |
| 家庭带娃 | 娃的体验定成败 | 家庭房/亲子酒店 | 儿童餐/软食 | 娃的状态抓拍 | 午睡刚需，就低不就高 |
| 家庭带长辈 | 省力+舒适 | 电梯房低楼层+含早 | 就近清淡 | 观景台优先 | 叠加省力慢游 |

**一人行细则**：自设疲劳红线（日行步数上限+最晚回程时刻），到点强制收；青旅挑有前台+电梯监控的；找"一人食友好"店（吧台/单人套餐/半份），错峰避包间尴尬；夜归走亮灯主干道；设报平安节奏；常用药+旅行险必备。

**省力慢游细则**（叠加时启用）：半天一个点+午休刚需；日行步数按其上限 70% 排；**能坐车绝不爬山**；台阶多的点给替代点；门口到门口优先，换乘 ≤1 次；电梯房+近景区+含早；就近优先于名店（名店排队久站=直接换近店）；代步费用单列一行（对体力一般成员是刚需不是可省项）；避雷新增三大隐藏雷——无座椅长排队区、台阶陡坡段、正午无遮挡段。

### 阶段 4.5 · 随行套件（与路书同步产出）

路书是**策划件**，随行套件是**执行件**——旅行中真正会被打开的是后者。
两者同文件或独立 HTML 均可，**但数据全部复用路书，不重写**。

**① 当日旅行模式（今天页）**
- 内容 = 今日动线（时间+地点+交通）+ 天气与穿衣 + 今日提醒（预约截止/加满油/带装备）+ 出片建议 + 顺路可买
- 按起飞日期自动算「今天」：今天高亮、已过天变灰；用户问「今天去哪」**直接切当日视图，不再翻全篇**
- 骨架 JS 已内置此能力，只需正确填 `TRIP` 日期映射

**② 特产三问卡**——每项回答三问：**是什么 / 哪里买 / 好不好带**
- 只推**方便携带**的（真空小包/密封礼盒/轻量装）；有携带条件的**高亮警示**（青稞酒仅托运、散装肉制品别买）
- 附比价提示（景区出口 vs 市区超市常差三成）；水分大的品类标注「认准产地直供，别买天价礼盒」
- 按「值得带的少数几样」给，**不铺清单**

**③ 面向长辈/官方的分发版——四件套**（骨架均已内置，只需确认开启）
- **当日模式**：按今天日期自动高亮并滚到当日卡片（行程期外则高亮「出发前清单」）
- **大字三档**：A−/A/A＋ 可调，localStorage 记忆
- **清单勾选**：出发前清单 + 装备单可打勾并持久
- **打印样式**：`@media print` 一键纸质化（隐导航、卡片防跨页撕裂）
- 🔴 **判据是「风格令牌 + 功能清单全带」，禁止只抄视觉皮**

> **配套原则：决策替做。** 面向长辈/官方/执行型读者，**分支决策提前替读者做完**，
> 输出指令式文本（"到了先看几点：中午前到 → 先吃面再玩…"），
> **不输出选项让读者选**——选项是给策划者的，指令才是给执行者的。

**④ 打卡清单**（特种兵模式专属，其他模式不出）
- 每个打卡点一行：`地名 + 核心机位/拍什么 + 预计停留分钟数`；**按动线顺序排，不按类别**
- 总行数 = 本趟计划打卡点总数，**数量本身就是特种兵的爽点，要显性给数字**（如「本趟打卡 23 个点」）
- 预留勾选框，收官行给「已完成 ___ / 计划 ___」计数位

**⑤ 每日配图**——见阶段 5 第 18 条。图源有实测结论，别重踩：

> 🔴 **`commons.wikimedia.org` / `upload.wikimedia.org` / `zh.wikipedia.org` / `api.wikimedia.org`
> 在境内直连网络全部不可达**——**不是偶发，别再等它通**。
> **首选 Pexels**（免费可商用，2 分钟注册）；有海外网络时 Wikimedia 可用，
> 其地标实拍质量高，但挑图纪律不能松。
> 地标类优先挑**真在当地的**；小众景点 Pexels 没有 → **同题材素材 + 标「（示意）」**，
> **绝不用别处照片冒充当地实景**。

### 阶段 5 · 交付自查（30 项机械核对）

**逐项打勾，全绿才可交付。但要看清那个「绿」覆盖了几项。**

> ⚠️ **脚本只能机械判定 30 项里的 23 项**（19 阻断 + 4 提示）。剩下：
> - **2 项条件项**——㉒ 停车信息（仅自驾）、㉓ 景区示意图（仅要求出图）
> - **5 项必须人工**——⑰ 信源店用透（要跨文件对情报卡）、⑲ 配图逐张亲验、
>   ⑳ 渲染截图亲验、㉔ 同一决策点全文同步、㉕ 修正双写（后两项要事实源↔HTML 对照）
>
> 每轮运行结尾都会打印「**本次实检 N/M**」和未覆盖清单。**不要把「全绿」读成「30 项全过」**，
> 也不要在交付说明里回避「哪些检查没做」——那是这套 skill 的立身之本。

**A 组·证据与溯源**（本 skill 独有）
1. **数字溯源报数**——所有距离/时长/票价/余票逐条有来源和时戳，`grep` 无裸数字
2. **证据分级标注**——每条推荐有 `[A]/[B]/[C·单源]/[D]` 标记（渲染成 `.ev` 徽章），
   `[D]` 项已给用户人工确认方式。**全篇零标记即拦下**
   > **✅ 2026-09-27 已补齐**：事实源模板示范了写法、`render_html.py` 把 `[A]/[B]/[C·单源]/[D]`
   > 转成 `.ev` 徽章、基准骨架有对应样式——本项**已升回阻断级**（全篇零等级标即拦下）。

3. **A 级信息时效**——动态信息（车次/票价/航班）在有效期内，超期已重查
4. **矛盾项并列**——多源冲突处已并列写出并注明来源，未擅自裁决
5. **能力降级已声明**——阶段 1 测出的不可用项，在路书中明确写出"哪些检查没做"
6. **未核实项清单**——所有 `[D]` 项汇总成清单，含用户确认方式

**B 组·内容完整**
7. 信息全文一致（无已取消项残留）
8. 天气已分时段
9. 门票放票时间+预约截止已标
10. 店铺有地址+营业状态已核
11. 动线无回头路
12. 预算闭合且隐藏成本有行
13. 避雷全是"真实场景+应对"
14. 应急 Plan B 覆盖关键环节
15. **六维度板块齐全**——吃/玩/住/行/拍/避雷逐项问"呈现在哪"（允许融合，不允许无板块）
16. **餐行机械钩报数**——逐日早/午/晚 grep 报数
17. **信源店用透**——每个收录店在清单或备选池里有自己的行，禁止只躺在情报卡

**C 组·交付物质量**
18. **每日配图齐全**（HTML 交付）——`figure` 个数 ≥ 行程天数，每张亲验真渲染（`naturalWidth>0`），四档视口（320/390/768/1280）无横向溢出。非实拍已标「（示意）」+页脚注明图源。**这项必须出数字，不许凭印象说"有图"**
19. **配图逐张亲验**——图注落位对 ≠ 图内容对，换源后逐张导出人工看
20. **页面已渲染截图亲验**——真机视口桌面+手机各至少一张
21. **HTML 入场动效两态实测**——动效禁裸 `opacity:0`（必须 `html.js` 门控+兜底），JS 禁用/启用两态内容全可见
22. **停车信息已查**（自驾时）——每天卡片底部 🅿️ 专条齐，查不到标"以现场为准"不许留空
23. **景区示意图**（必出时）——六要素齐+手机视口截图亲验缩放可读

> 💡 **⑱⑳㉑ 的本机执行方式**：`python "<SKILL_ROOT>/tools/shoot.py" 路书_XX.html --shot --outdir 截图目录`
> ——先跑四档 iframe 溢出探针（320/390/768/1280），再按 `--shot-widths`（默认 768,1280）出图，**须 ≥496px**。
> ⚠️ 无头浏览器**最小视口约 496px**，`--window-size=375,...` 不会缩到 375 而是**原地裁剪**；
> 所以**真机手机视口（375/390）用本工具截不了**，⑳ 的「手机一张」须真机或有移动模拟的浏览器补，缺了就如实写。

> 本机 `agent-browser` 未装、无 Chromium 缓存时，`shoot.py` 会自动改用系统 Edge/Chrome。

**D 组·一致性与口径**
24. **同一决策点全文同步**——动一个时间/价格/店名前，grep 出该点在全文所有落位（准备清单·速览·时段卡·示意图·门票表·避雷·预算表·应急），一处改全部改。**判据=旧值在"活条款"里归零**（版本史里对旧写法的引用要保留）
25. **修正双写**——事实源 JSON 已同步更新，JSON-HTML 关键决策点一致性抽查通过
26. **文案去 AI 味**——grep 高频词（进行/值得注意/本质/仿佛/映入/众所/首先其次/综上/绝绝子/震撼/为您/不仅…而且/此外/标志着）+ 通读标题与各板块：称谓口语化、无 ≥3 句书面排比、无"不像人话"的句子。**路书是给普通人执行用的，不是给读者欣赏的——像朋友交代攻略的口吻，不是旅游杂志文案**

**E 组·情报覆盖**（社会情报是默认动作，做了没做都要留痕）

27. **社会情报已声明**——正文里必须能读到阶段 3.5 的交代，二选一即为过：
   - **已采集**：写明「情报来源」+ 走的是哪条路径（官方文旅发布 / 搜索引擎索引 / 用户投喂）+ 提了几条；
   - **未采集**：写明「本次未采集社会情报」+ 理由（纯过境 / 用户不要 / 无公开内容）。
   **两者都没有 = 拦下**——跳过默认动作可以，静默跳过不行。
   > 落地方式：填事实源的 `meta.social_intel`，渲染器会自动把它注入 `#overview` 顶部。
   > 判据是**留痕**不是**必须采到**，所以「如实报没采」同样算过。

**B 组·内容完整（续）**（路线结构——读者要能对比方案）

28. **主路线 + 备选路线齐备**——一条主线 + **≥2 条备选**。用户要的是「能对比」，
    不是「给一条路走到黑」。
   - **主线**写清：叫什么、一句话怎么走、**途经哪几站**、什么情况走它；
   - **备选**可以简略，但每条必须带**「什么情况走它 + 代价 / 依赖」**两件套——
     只列地名不写代价，等于把决策又推回给用户。
   > 落地：填事实源顶层 `routes`（`primary` + `alternatives[]`），渲染器把主线注入
   > `#drive`、备选注入 `#boost`。**注入既有区块、不新开 section**——骨架一动，
   > 版式指纹与全部示例的逐字节基线会一起失效。

29. **沿途顺道点已声明**（提示级）——主线上**没排进去、但顺路值得进去**的点，
    补「在哪一站附近 + 距离 + 一句说明」。
   > 落地：填 `days[].nearby`，渲染器注入 `#drive`。
   > ⚠️ **每一条都要核过开放日**——「顺道去看看」最怕到了门口才发现那天闭馆。
   > 采点用 `nearby-spots` 命令（高德周边搜索），但它返回的常常包含**景区自身的组成部分**
   > （园内亭台、馆内旧址之类），筛的时候要认出来，别当成额外顺道。
   > 沿线确实没有可顺道的点时，写明原因，别静默略过。

30. **个性化偏好已声明**（提示级）——阶段 0 采集到的**用户自报**偏好（饮食忌口/喜好、
    作息与休息、兴趣），在主路线区呈现为「按你的偏好排的」。
   > 落地：填事实源顶层 `preferences`（`diet` / `pace` / `interests`），渲染器注入 `#drive`。
   > ⚠️ **只呈现用户原话，绝不呈现模型推断**——推断会冒充采集值，违背「每个数字都有来源」。
   > 这是软字段（`intake.py` 缺省进 `assumptions`）：没采集不拦，采集了却不呈现才提醒。

**九道硬闸门，各拦一类错误**：

| 闸门 | 拦什么 | 不绿的处置 |
|---|---|---|
| 版式一致性 | 有人手改 HTML 的 `<style>` / 漏了导航入口 / 留了占位符 / 配图少于天数 | 回到 JSON 重渲染，**别修 HTML** |
| 可行性 `INFEASIBLE` | 排不通的行程（闭馆时间、换乘余量、预算不闭合）；**以及 `EMPTY_ITINERARY`——没有可检查的内容** | **不得作为可执行方案交付**；调时间 → 加缓冲 → 换交通 → 换顺序 → 移天 → 砍可选点，最多修 3 轮。报 `EMPTY_ITINERARY` 时**别去改行程**：先确认文件没喂错（要带 `activities` 的 `itinerary_*.json`，不是方案层 `final_plan_*.json`） |
| 方案 `INVALID` | 景点缺特色/理由/来源，或内嵌的机票酒店报价有硬伤 | 补齐后再交；**未被引用的坏报价同样让方案失败** |
| 30 项未全绿 | 内容层的裸数字 / 空洞避雷 / 餐行缺失 / AI 味 / 情报未声明 / 缺主路线或备选路线 | 未完成，不许交付。**注意脚本只机械判定 23 项**——未覆盖的 7 项要人工过一遍，并在交付说明里写清楚 |
| 源核验 `source_audit` 有 FAIL | 徽章标注违反证据纪律：`[A]` 说不出来源与时戳、`[B]` 数不出第二源、门票价/车程/时刻落在 `[C]`（死线）、`[D]` 没给出路、source_ref 悬空、同一 POI 两处评分打架 | 回到事实源改**标注与写法**（不是删徽章）：能补来源就补，补不上就如实降 `[D]` 并给用户可自查的出路 |
| 精简版 `compact_check` 有 FAIL | 精简版被压坏了：强制约束的数字（末班/停止入园/寄放/留足余量/行程时长）丢了、证据标记被删光、根本没写 compact 档 | 回事实源补 `compact` 档，**别靠删内容求短**（见 `references/dual-version.md`） |
| 声明比对 `claim_audit` 有 FAIL | **实采值没有如实进路书**（内容真实第 1 层）：itinerary 留痕里的段时长与段车费，在事实源全文中找不着——采集 16 分钟写成 15 分钟、实采 25 元写成 20 元这类数字幻觉在这里现形 | 修事实源的数字（以留痕为准），或删掉已不进路书的留痕段再跑 |
| 来源回声 `echo_audit` 有 FAIL | **死线类声明在引用页里找不到值**（内容真实第 2 层）：线索卡 claim 声称的数字/时刻，抓回来的页面正文里没有——「引用了官网却写了个页面上没有的价」在这里现形。UNREACHABLE（403/风控/断网）只 WARN 不判死——「看不到」不是「没有」 | 重查该来源并更新数值与核实日期；若页面在核实日期之后合法改版，更新时戳重跑 |
| 独立源 `cross_check` 有 FAIL | **转引充双源**（内容真实第 3 层）：`[B]` 依赖的两个「独立源」正文重合超阈值——互相转载的一家，双源地基是假的 | 换真正的第二来源，或如实降 `[C·单源]`；重合低于阈值的高明洗稿兜不住，靠人工 |

> ⚠️ **上表里最容易被误读的一行是「源核验」——它的能力边界必须说清。**
> 源核验审的是**标注纪律**（标得配不配：有没有来源、有没有时戳、有没有越死线、
> `[D]` 有没有给出路），**不审内容真实**（标了 `[A]` 的那句话是否真在所引来源里）。
> 换句话说：**「过了源核验」= 「你说得出这个数字是哪来的」，≠「这个数字一定对」。**
> 内容真实由**三层链**接力（2026-10-01 全部落地，见上表后三行）：
> ① `claim_audit`（v2）：高德采集默认留痕（快照内嵌 `raw_calls`），实采段时长与
> 段车费必须如实进路书，被改/被丢即 FAIL——留痕证明「声明与采集一致」，
> 不证明「采集与世界一致」；② `echo_audit`：抓取线索卡引用页正文，验证声称的
> 数字/时刻/关键短语真的在页面上——但「页面里有」≠「页面说的对」，且 JS 渲染页
> 抓不到、页面合法改版会造成时戳错位，这两类如实列 UNREACHABLE/WARN 不判死；
> ③ `cross_check`：把各来源页面正文做重合比对，拆穿「互相转载充双源」——但
> 重合低于阈值的高明洗稿兜不住。**三层全过仍 ≠「数字一定对」：链条止于
> 「页面怎么说」，引用页自身的对错要人工临行复核**，未核实项清单是最终兜底。
> 详见 `references/source-audit.md` 的「局限」章与 `references/echo-cross.md`。

**另有一道不阻断的「时效体检」**（`freshness.py`）：它把「这张票到出发那天还新不新」
从文档里的表格变成可执行判据。中山实测报出**3 条门票已超时效、14 条路线待出发日重算**。
**报出须重查不等于写错了**——它是一张「出发前照着打勾」的清单，
和四条死线是同一件事的两面：死线管「能不能写」，时效管「写到哪天为止还作数」。

脚本返回结构化结果，**消费 JSON 而非解析终端文字**。
退出码：`0` 通过 ｜ `1` 执行出错 ｜ `2` 校验未通过 ｜ `3` 证据不全（`INCOMPLETE_EVIDENCE`）。

### 阶段 5.5 · 交付分发（把路书交到用户手上）

**闸门全绿之后，路书还躺在电脑上——这一步走完才算交付。**

**交两版，不是一版**：完整版与精简版一起给，并**说清哪版什么时候用**——
「路上照着走用精简版；查价格、翻备选、比住宿的时候开完整版」。
只给一版是常见失误：给完整版嫌长，给精简版又会在用户想查细节时找不到东西。

路书是**单文件自包含 HTML**（配图 base64 内联、0 个外部依赖），所以传输方式很自由。
按实测可靠性排序，**优先走第一条**：

| 顺序 | 方式 | 实测结论 | 代价 |
|---|---|---|---|
| ① **微信传文件** | 电脑微信 → 文件传输助手 → 拖入 `路书_XX.html` → 手机点开 → 「···」→ 用其他应用打开 → 浏览器 | **唯一实测有效的路径**，零网络依赖、不挑运营商 | 微信里不能直接预览，多两步点击 |
| ② 在线链接 | 用 `sites` 能力发布（发布目录入口必须叫 `index.html`） | 服务端可靠（HTTP 200 + 四个公共 DNS 全解析通过），但**实测某手机在流量网络下打不开** | 公开可见；改完必须重新 cp + 重新发布 |
| ③ 同 WiFi 局域网 | `python -m http.server` + 局域网 IP + 二维码 | **尚未验证** | 出了这个 WiFi 就失效；服务须 DETACHED_PROCESS 起，防火墙须放行 |

**手机端点开打不开时，先对号入座**（`.html` 是**文件**不是网页，最容易卡在这）：

| 表现 | 真实原因 | 处置 |
|---|---|---|
| 微信里提示无法打开 / 一直转圈 | **微信不把 `.html` 当网页渲染**，只当普通文件 | 手机上点开该文件 → 右上角 **「···」→「用其他应用打开」→ 选浏览器**。不走这一步，文件就是打不开的 |
| 白屏 | 多半是把 `127.0.0.1:xxxx` 的**本地预览地址**当链接发给了手机 | `127.0.0.1` 指手机自己，必然打不开。改传文件 |
| 满屏代码 | 被文本预览器打开了 | 同上，改用浏览器打开 |

> ✅ **产物侧的原因已排除**（2026-09-28 本机实测）：本包 HTML 是单文件自包含——
> 0 个 http(s) 外部引用、配图 base64 内联、UTF-8 与 `viewport` 声明齐全、
> `localStorage` 的 4 处调用**全部包了 `try/catch`**（iOS 在本地文件下禁用存储，
> 也只会丢「字号记忆 / 勾选记忆」，不会白屏）。所以**打不开基本都不是文件的问题，
> 是打开方式**。
>
> ⚠️ 「用其他应用打开」的候选列表里**不一定有 Safari**（随 iOS 版本与文件来源变化）；
> 具体菜单项名称**未在真机实测**，以实际菜单为准——找不到就先用「存储到文件」中转。
> **交付时别只丢一句「微信发给你」**：要把「··· → 用其他应用打开」这两步一起说清，
> 否则用户会以为文件坏了（2026-09-28 实际发生过一次）。

**分发前必做**：

- 传文件用**源文件**，不要用发布目录里的副本（副本是留给线上用的）。
- 走在线链接时：发布目录里放的是**副本不是软链**，改完路书必须重新 `cp` 再重新发布，
  否则线上还是旧版；且每次发布都要重新取得用户同意。
- ⚠️ **别承诺「链接一定能打开」**。已实测：`*.app.workbuddy.host` 在服务端正常、
  四个公共 DNS（阿里/腾讯/114/本机）全部解析成功的情况下，用户手机仍然打不开——
  根因在手机侧网络，不在路书。遇上打不开，按 ① → ③ 换路子，别让用户反复重试同一个链接。

**交付时一并说清三件事**（这就是与「把文件甩过去」的区别）：

1. **未核实项清单**——`[D]` 项逐条列出，每条带用户可自行确认的方式（打哪个电话 / 看哪个公众号 / 去哪比价）
2. **本次真正跑了哪些检查**——覆盖声明的「实检 N/M」与未覆盖项，尤其没做的 ⑲ ⑳
3. **配图性质**——AI 生成或图库素材都要说明，标了「（示意）」，**不是当地实景**

> 📄 **附一页可信度概览**（推荐，2026-10-25 起有工具支撑）：
> ```bash
> python "<SKILL_ROOT>/tools/evidence_report.py" 路书_XX.json
> ```
> 把上面三件事里的 ①② 汇成单文件 HTML《可信度概览》（徽章分布 / 闸门状态 /
> 须重查清单 / [D] 清单），交付时随路书一起发。**它是报告不是评分**——
> 报告是交代，分数会诱发刷分。

### 阶段 6 · 行程中陪伴 / 复盘回流

**临行前 3 天 · 两件事一起做**（这是「时效」与「天气」的唯一正确时点）：

```bash
# ① 时效体检：把出发日当基准，看哪些数字已经过期
python "<SKILL_ROOT>/tools/freshness.py" 路书_XX_事实源.json --strict
#    须重查的门票/房价/车次逐个回原渠道复核；路线类回高德跑一次 amap-snapshot 整批刷新

# ② 天气：这时才查得到真预报（高德窗口只有 4 天，早查无意义）
python "<SKILL_ROOT>/tools/travel_planner.py" weather --city 中山市 --start 2026-09-28 --end 2026-09-30

# ③ 公告复扫：闭馆/调价/管制类事件按同一节奏重查一遍（预算不够就砍 EVENT 类）
#    命中的变更走 --check 分级后更新 meta.bulletin，首屏公告条随之刷新
python "<SKILL_ROOT>/tools/bulletin.py" --plan --facts 路书_XX.json
```

- **路书里不写未来天气**——写下的多半会变。要写就写「出发前 3 天查一次」。
- 天气命令只报**预报说了什么**，不替行程做决定；标出雨天只是提醒那天留个室内备选
  （中山实测：9/30 白天晴、**夜间雷阵雨**，正好是安排东堤日落那天）。
- 城市名要写全（「**中山市**」而不是「中山」）：简名带 `all` 会报 20003，
  带 `base` 会静默返回**大连市中山区**。最稳是直接给 adcode（如 `442000`）。

**陪伴模式**（已出发在路上的三种状态）：
- **已出发在路上**：即时问答 + 当日精排
- **已到目的地**：当日/次日逐时段精排
- 当日调整后**必须回写事实源 JSON**；改版前后跑一次改版审计——
  ```bash
  python "<SKILL_ROOT>/tools/revision_audit.py" 路书_XX_v1.json 路书_XX.json --strict
  ```
  数值变化与等级升降逐条现形；降级（如重查后 [A]→[D]）在 `meta.revision_log`
  登记 `{about, from, to, reason}`——**降级不禁止，禁止的是无声**。

**复盘回流**（事件触发，不是每次生成都复盘）：

触发条件、模板、出口与 LLM 边界见 `references/retro-protocol.md`，四句话版——
① 只有**闸门 FAIL 或用户打回**才触发复盘（全绿轮次没有经验，只有噪声）；
② 每条复盘按六字段模板追加进 `references/experience.md` 的「本机记录」区
（现象 / 根因 / 触发条件 / 是否目的地特定 / 出口 / 提交号，缺一不算完成）；
③ 教训**必须有去向**：目的地特定→事实源，可规则化→闸门 RULES+负向样本，
写不成规则→标 `[人工维持]` 明示自觉区——悬在散文里的教训等于没有
（`desource` 文档命令错误就悬了两个月）；
④ 根因与出口判定**人仲裁**——LLM 起草，错误泛化进生成链路是负反馈不是改进。
**价值不在规矩，在规矩后面的翻车实录**——下次触发时先读这里。

**外部依赖**（都可降级，`doctor.py` 会如实报告各自状态）：

- **地图服务（高德）**：POI 与路线核验。三级配置任选其一——
  ① 环境变量 `AMAP_API_KEY`　② `~/.verified-travel-planner/credentials.json`（形如 `{"amap": "你的key"}`）　③ macOS 钥匙串。
  这里的 `~` 指 **Python 的 `Path.home()`**：Windows 上是 `C:\Users\<用户名>\.verified-travel-planner\credentials.json`。
  ⚠️ Git Bash 里的 `~` 可能被 `HOME` 环境变量改指到别处（本机实测指向 `AppData/Roaming/SPB_16.6`），
  去那里 `ls ~/.verified-travel-planner/` 会报不存在，**别据此判断 key 没配上**——
  以 `credential-status` 的输出为准。

  **配置就用随包工具，别手工写文件**（key 不回显、不进 shell 历史，写入前自动备份）：
  ```bash
  python "<SKILL_ROOT>/tools/set_amap_key.py"                 # 交互输入 key 并写入
  python "<SKILL_ROOT>/tools/set_amap_key.py" --verify        # 真连一次高德，验证并翻译报错
  python "<SKILL_ROOT>/tools/set_amap_key.py" --status        # 只读状态
  ```
  验证失败时它会按高德的 `info` 枚举名给出「该去控制台改哪个选项」的具体建议。

  **配好之后跑这 4 步验收**（顺序即依赖顺序，前两步不通过别急着采集）：
  ```bash
  python "<SKILL_ROOT>/tools/travel_planner.py" credential-status   # 1 看 key 配没配上、从哪读到
  python "<SKILL_ROOT>/tools/travel_planner.py" doctor --live       # 2 真连一次高德 + 本机能力体检
  python "<SKILL_ROOT>/tools/travel_planner.py" search-places --keywords "珠海长隆海洋王国" --city 珠海 --limit 2
  python "<SKILL_ROOT>/tools/travel_planner.py" amap-snapshot --input 输入.json --output 快照.json
  ```
  通过判据：① 输出 `{"status": "CONFIGURED", "source": "file"}`；
  ② `core.amap.status` 为 `READY` 且带 `result_count`，同时 `environment` 里 3 项 critical 全 `READY`；
  ③ 返回带 `longitude/latitude/provider_id/rating` 的真实 POI；④ 快照里 `provenance.live_data` 为 `true`。
  ⚠️ 命令名是 `credential-status`（子命令），**不是** `--status` 这种全局开关——写成 `--status` 会得到
  `error: the following arguments are required: <命令>`。
  ⚠️ `doctor` 默认会自己猜客户端。装了几个客户端时「哪个在跑我」是读不出来的——报告里的
  `client_candidates` 列全部痕迹、`client_ambiguous` 说是否多于一。**显式带 `--client`
  才是真实结论**（可选 `workbuddy` / `zcode` / `codex` / `claude-code`）。

  ⚠️ **`amap-snapshot` 的 `origin`/`destination` 必须是「居民点级」实体（城市、区县）**，
  输入格式：
  ```json
  {"origin": "广州市", "origin_city": "广州",
   "destination": "珠海市", "destination_city": "珠海",
   "route_modes": ["transit", "driving"]}
  ```
  传具体 POI（如 `"珠海站"`「某餐厅」）会被覆盖门禁**主动拒绝**，报
  `Amap 未能可靠定位「珠海站」：查询的是城市或地区，却匹配到「兴趣点」级别的地点`。
  这**不是 bug，是防误匹配的设计**——高德查境外地点不返空而返同名国内地点，
  所以「城市级」查询必须走 `geocode(expect_settlement=True)` 做真实覆盖检查。
  城内具体景点/车站的坐标用 `search-places`（POI 级）拿，两条通道别混用。
  验收通过的快照里 `locations.origin.match.level` 应为 `"市"`、`confidence` 为 `"HIGH"`。

  ⚠️ **采集即留痕（P1 来源留痕，2026-09-30 起默认行为）**：快照默认内嵌
  `raw_calls`（每次成功调用的原始返回体，key 已脱敏）——**别用 `--no-keep-raw`
  放弃它**，声明比对闸门靠这份留痕才能复核「实采值有没有如实进路书」。
  `search-places` / `nearby-spots` 用 `--trace <文件>` 把本次调用同样落盘。
  交付前 `ship.py` 会跑 `claim_audit`：itinerary 留痕里的段时长必须在事实源
  全文中可寻——采集 16 分钟写成 15 分钟会在这里 FAIL。留痕证明
  「声明与采集一致」，不证明「采集与世界一致」，边界别读成保证。

  **无 key 时**：POI 与路线相关项一律降级 `[D]`，不得用模型推断的坐标或车程冒充已核实。
  也可用 `travel_planner.py doctor --live` 实测（同样真查一次「北京 天安门」）。
  ⚠️ **key 绑定的服务平台必须选「Web服务」**——本 skill 走 `restapi.amap.com`，选成 JS API / Android / iOS 会报 `USERKEY_PLAT_NOMATCH`。
  注意控制台是**两层**的：先建「应用」（应用名称 + 应用类型），再在应用里「添加 Key」（服务平台）。
  **应用类型不影响 Key 权限**——下拉里有「Web服务」就选它，是行业分类（出行/生活服务/其他）就选「出行」或「其他」，随便；
  真正决定成败的是第二层的「服务平台」。
  ⚠️ **IP 白名单留空**——家庭宽带 IP 是动态的，设了白名单迟早调不通。
  ⚠️ **不要启用「数字签名」**——引擎不带 `sig` 参数。但注意它是**可选功能、默认未启用**：
  Key 创建表单里**没有**这一项（实测，别去找），也不需要专门找开关去「关」它。
  只要不去配置「安全密钥」，签名就不生效，带 key 直连即可。
  ✅ **最好的选对自检信号是「可用服务」那一行**：选对 Web服务 后它应列出 REST 服务清单
  （地理编码 / 逆地理编码 / 搜索 / 路径规划 / 天气 等）；若显示的是
  「Javascript API / 地图组件 / 室内地图 JS API / 地铁 JS API」，说明选的是 Web端(JS API)，必须改。
  ⚠️ 用环境变量方式**要重启 WorkBuddy**（skill 跑在它进程里，继承的是启动时的环境）；用凭据文件则立即生效。
  ⚠️ **个人认证的配额很低**：关键字/周边搜索是 **100 次/日** 量级（地理编码、路径规划 5000 次/日）。
  做路书时收紧搜索次数（一次搜索多取结果、复用已采集快照），配额每日 0 点重置。
  另注意 `geomatch` 那条陷阱：高德查境外地点**不返回空结果**，而是返回名称相近的国内地点，坐标看着完全正常。
- **铁路查询（12306）**：车次与余票。**本包不含安装配套**——`doctor` 会检测 `mcp-server-12306/` 运行时而报
  `MISSING`，但仓库里**没有** `setup_rail_mcp.sh` / `rail-mcp.md` / `patches/`（上游那几件没随包搬过来），
  所以别照着旧提示去装（该提示已改成如实说明）。实测（2026-09-27）可获取的 MCP 市场里**没有 12306 官方 server**，
  只有第三方 OTA／差旅聚合（同程程心、途牛等）提供火车票查询——接上也只能算 `[B]`（第三方聚合），**不能当 `[A]`**。
  结论：铁路项**默认走只读网页核验 `[C]` 或标 `[D]`**；要接入须自备第三方 stdio MCP——
  它会执行本地代码，落地前先做安全审查（上游社区连接器还明确声明不用于商业用途）。
- **配图源**：Pexels 等免费图库（需自注册 key）。不想注册可用 AI 生图，规矩只要求每天配图 + 非实拍标「（示意）」+ 页脚注明来源
- **`tzdata`**（Windows 需要）：Python 在 Windows 上不自带时区数据库，
  缺它时可行性检查会回退到用时间戳自带的偏移量并给出警告，
  `doctor` 会把「时区数据库」报成 `DEGRADED / ZoneInfoNotFoundError: No time zone found with key Asia/Shanghai`。
  想拿到完整时区校验（跨时区行程必须）就装上——**用阿里源**：
  `pip install tzdata -i https://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com`
  ⚠️ 实测本机清华源 `pypi.tuna.tsinghua.edu.cn` 对 `tzdata` 返回
  `No matching distribution found`（索引里查无此包），阿里源一次装成。换源不是可选项，是必须。
  装完重跑 `doctor`，「时区数据库」应转为 `READY / Asia/Shanghai 可解析`。
  它装进的是 skill 实际调用的那个解释器（写在 `doctor` 输出里的 `python.version` 对应路径），
  装到别的 venv 里 `doctor` 看不见。

- **发布前跑两条命令**：`doctor.py`（保证别人跑得起来）+ `validate_skill.py`（保证文档没撒谎）。
  打包时 `.gitattributes`（`* -text`）与 `assets/` **不能少**——前者关系逐字节回归基线，后者缺了直接拒渲染。
